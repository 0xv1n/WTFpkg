Candidates below are distinct from the [current technique catalog](content/techniques/). Rank weighs novelty in this repo, defensive value, and strength of primary-source evidence (high/medium). The first three are the best choices for full technique pages.

1. **Python wheel `.pth` startup execution (pip/PyPI).** A wheel can place files directly in `site-packages`, and Python executes `import` lines in `.pth` files there at every normal interpreter startup, even if the package is never imported. Thus a hostile wheel can run code on a *later* `python` invocation without a source build; this is separate from `setup.py` or build-command hooks. [Wheel format](https://packaging.python.org/en/latest/specifications/binary-distribution-format/) [Python `site` documentation](https://docs.python.org/3.14/library/site.html) **Check:** inspect wheel members with `python -m zipfile -l package.whl` and installed `site-packages/*.pth` for executable `import` lines; review or remove untrusted `.pth` files and install packages in isolated environments. [Wheel format](https://packaging.python.org/en/latest/specifications/binary-distribution-format/) [Python `site` documentation](https://docs.python.org/3.14/library/site.html)

2. **Cargo compiler-wrapper configuration.** Cargo searches project and parent `.cargo/config.toml` files; `build.rustc-wrapper` names a program Cargo executes in place of `rustc`, passing the real compiler as its first argument. A hostile repository configuration can therefore run a wrapper during an ordinary `cargo build`, independent of a crate's `build.rs`. [Cargo configuration](https://doc.rust-lang.org/cargo/reference/config.html) **Check:** review `.cargo/config.toml`, parent configurations, and `RUSTC_WRAPPER`/`CARGO_BUILD_RUSTC_WRAPPER` before building an untrusted checkout; remove unexpected wrapper settings. [Cargo configuration](https://doc.rust-lang.org/cargo/reference/config.html)

3. **npm dependency `bin` command substitution.** A dependency's `package.json` `bin` field installs an executable into `node_modules/.bin`; `npm run` adds that directory to the script's `PATH`. If an attacker-controlled dependency supplies the command named in a project script, running that existing script can execute the dependency's binary, including when install scripts are disabled. [npm `package.json`](https://docs.npmjs.com/cli/configuring-npm/package-json/) [npm run](https://docs.npmjs.com/cli/commands/npm-run/) **Check:** resolve script command names against `node_modules/.bin`, inspect their target packages and `bin` fields, and pin or remove unexpected providers. [npm `package.json`](https://docs.npmjs.com/cli/configuring-npm/package-json/) [npm run](https://docs.npmjs.com/cli/commands/npm-run/)

4. **Bundler Gemfile and git gemspec evaluation (RubyGems).** A `Gemfile` is evaluated as Ruby code, and Bundler builds git-sourced gems by running `gem build`, which evaluates the repository's `.gemspec`. Running Bundler in a hostile Ruby project or using a hostile git dependency can therefore execute Ruby while resolving or building dependencies, before application code runs. [Bundler Gemfile reference](https://guides.rubygems.org/gemfile/) **Check:** inspect `Gemfile`, `eval_gemfile` targets, and git/path-sourced `.gemspec` files before `bundle install`; pin git dependencies to reviewed commits. [Bundler Gemfile reference](https://guides.rubygems.org/gemfile/) [Git gem guide](https://guides.rubygems.org/git/)

5. **npm root `overrides` dependency replacement.** Root `package.json` `overrides` can replace a transitive dependency with another package, including an `npm:` alias, local file, or Git URL; overrides inside installed dependencies are ignored. A hostile change to the root manifest can silently redirect a trusted dependency name to an attacker-controlled implementation. [npm `package.json`: overrides](https://docs.npmjs.com/cli/configuring-npm/package-json/#overrides) **Check:** review root `overrides` alongside dependency and lockfile changes, especially replacement specifiers; remove unapproved replacements. [npm `package.json`: overrides](https://docs.npmjs.com/cli/configuring-npm/package-json/#overrides)

6. **Homebrew formula service persistence.** A formula's `service` stanza can name a background command. `brew services start` starts it immediately and registers it for login when run as a user or for boot when run with `sudo`. A hostile trusted third-party formula or compromised official formula can therefore define persistent execution that begins when a user or automation starts the service. Non-official formulae require explicit trust by default. [Formula Cookbook: service files](https://docs.brew.sh/Formula-Cookbook#service-files) [Homebrew manpage: services](https://docs.brew.sh/Manpage#services-subcommand) [Homebrew Tap Trust](https://docs.brew.sh/Tap-Trust) **Check:** inspect `brew cat <formula>` for `service do` and its `run` target, then use `brew services list` to find active services and stop unapproved ones. [Formula Cookbook: service files](https://docs.brew.sh/Formula-Cookbook#service-files) [Homebrew manpage: services](https://docs.brew.sh/Manpage#services-subcommand)

7. **APT pin priority forced downgrade.** APT's preferences files control version selection, and priority 1000 or higher allows a downgrade that default priorities would prevent. An attacker who can alter those files can steer a later install or upgrade toward an older vulnerable version from a configured repository. [Debian `apt_preferences(5)`](https://manpages.debian.org/bookworm/apt/apt_preferences.5.en.html) **Check:** inspect `/etc/apt/preferences` and `/etc/apt/preferences.d/` for high-priority pins, and run `apt-cache policy <package>` to see candidate priorities before upgrades; remove unapproved pins. [Debian `apt_preferences(5)`](https://manpages.debian.org/bookworm/apt/apt_preferences.5.en.html) [Debian `apt-cache(8)`](https://manpages.debian.org/bookworm/apt/apt-cache.8.en.html)

8. **dpkg trigger-delayed `postinst` execution.** A package can declare interest in a trigger through `DEBIAN/triggers`; dpkg later calls its `postinst triggered` action when that trigger fires. A malicious package can therefore arrange another execution point after its initial configuration, including activity initiated by a different package. [Debian `deb-triggers(5)`](https://manpages.debian.org/unstable/dpkg-dev/deb-triggers.5.en.html) [Debian `deb-postinst(5)`](https://manpages.debian.org/unstable/dpkg-dev/deb-postinst.5.en.html) **Check:** inspect a downloaded `.deb` with `dpkg-deb --ctrl-tarfile package.deb | tar -tf -` and review its `triggers` and `postinst` control members together; remove untrusted trigger registrations by removing the package. [Debian `dpkg-deb(1)`](https://manpages.debian.org/unstable/dpkg/dpkg-deb.1.en.html) [Debian `deb-triggers(5)`](https://manpages.debian.org/unstable/dpkg-dev/deb-triggers.5.en.html)
